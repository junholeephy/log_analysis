# 필터 규격 — 무엇을 골라 어떤 모양으로 넘기나

> **이건 이 프로젝트의 사정이다.** 필터 로직이 운영 쪽에 이미 있고 그걸 쓰기로 했다.
> 다른 배포라면 이 저장소의 `src/ragdiag/filters.py` 를 그대로 써도 되고, 그러면
> 이 문서는 필요 없다 — `--filter-data` 로 필터 JSON 을 주면 끝이다.

필터는 **운영 환경 쪽에서 구현한다.** 이 저장소의 `src/ragdiag/filters.py` 는 여기서
검증할 때 쓰는 것이고, 실제 선별은 그쪽 로직을 쓴다.

이 문서는 그 경계를 정한다 — 필터가 **무엇을 내놓아야 하는지**, 받은 쪽이 그것으로
**무엇을 하는지**, 그리고 **어디서 조용히 어긋나는지**.

```
로그 ──▶ [필터: 운영 환경 구현]  ──▶ 턴 목록 ──▶ [짝짓기 + 판정: 이 저장소] ──▶ 결과
          어느 턴을 볼 것인가        id + turn      직전 턴과 엮어 Case 로
```

---

## 1. 필터가 정하는 것은 하나다 — 어느 턴을 볼 것인가

필터의 출력은 **턴 지목 목록**이다. 답변을 고르는 것도, 청크를 고르는 것도 아니다.

```json
[
  {"user_id": "EMP-0001", "conversation_id": "C-0001", "turn": 3},
  {"user_id": "EMP-0002", "conversation_id": "C-0007", "turn": 2}
]
```

JSONL 도 그대로 받는다. 파이프라인이 한 줄에 하나씩 뱉는 경우가 흔하고, 그것 때문에
변환 스크립트를 하나 더 짜게 만들 이유가 없다.

```
{"user_id": "EMP-0001", "conversation_id": "C-0001", "turn": 3}
{"user_id": "EMP-0002", "conversation_id": "C-0007", "turn": 2}
```

| 키 | 필수 | 설명 |
|---|---|---|
| `conversation_id` | ✔ | `conv_id` 로 적어도 받는다 |
| `turn` | ✔ | 정수. **불만이 표현된 턴**이다 (비판받은 답변의 턴이 아니다) |
| `user_id` | 권장 | 원본·마스킹본 어느 쪽이든 된다 |

**`user_id` 를 권장하는 이유** — `conversation_id` 가 사용자마다 겹칠 수 있다. 겹치면
어느 대화인지 정할 수 없으므로 **거절한다.** 아무거나 골라 남의 대화를 판정하는 것보다
낫다.

```
대화 id 가 여러 사용자에게 있어 어느 것인지 정할 수 없습니다 (12건, 예: C-0001).
  목록에 user_id 를 함께 넣으세요.
```

### 실행

```bash
python log_analysis/src/run.py --conv-data <로그> --turns <목록>
```

`--turns` 를 주면 **이 저장소의 필터는 돌지 않는다.** `--filter-data` 와 같이 주면
거절한다 — 둘 다 "어느 턴을 볼지"를 정하는 것이라, 같이 주면 무엇이 적용됐는지
알 수 없다.

라벨 실값(`labels.query` / `labels.emotion`)도 필요 없다. 무엇을 볼지는 이미 정해져서
왔기 때문이다.

## 2. 받은 쪽이 하는 일 — 짝짓기

지목된 턴 하나가 `Case` 하나가 된다. **이 짝짓기는 이쪽 코드가 한다** (`conv.to_case`).

```
turn 2   질문 "국내 출장 식비 상한이 얼마인가요?"
         답변 "규정에 따라 지급되며 부서별로 다를 수 있습니다."   ◀── 판정 대상
         청크 ["국내 출장 식비는 1일 3만원을 상한으로 한다.", ...]  ◀── 대조 대상

turn 3   질문 "그래서 얼마라는 건가요?"       ◀── 지목된 턴. 불만이 여기 있다
```

| Case 필드 | 어디서 오나 |
|---|---|
| `current_query` | **지목된 턴**의 `user_question` |
| `llm_ans_on_last_q` | **직전 턴**의 `llm_response` |
| `rag_chunks` | **직전 턴**의 `retrieved_data` |
| `pre_queries` | 지목된 턴 이전의 질문들 (최근 `history_turns` 개) |
| `dept` · `job_grade` · `job_name` · `position_name` | 사용자 메타 |

> **왜 짝짓기를 이쪽에 두나.** 짝을 하나 밀리면 **엉뚱한 답변을 판정한다.** 그런데
> 그 결과는 그럴듯해 보인다 — 에러도 안 나고, 라벨도 붙고, 표도 채워진다. 양쪽에서
> 각자 구현하면 어긋나도 드러나지 않는다. 그래서 선별은 그쪽, 짝짓기는 이쪽이다.

---

## 3. 여기서 조용히 어긋난다

### ① 앞 턴을 버리면 안 된다

지목한 턴만 남기고 로그를 줄이면 **전부 0건이 된다.** 직전 턴의 답변이 곧 판정
대상이기 때문이다.

```
❌ turn 3 만 남긴 로그  →  판정할 답변이 없다
✅ turn 1~3 이 있는 로그 + "turn 3 을 봐라"는 목록
```

로그는 **줄이지 말고 그대로 넘기고**, 무엇을 볼지는 목록으로 말한다. 목록이 곧
필터이므로 로그를 또 자를 이유가 없다.

이 경우 이렇게 나온다:

```
  후속 턴 7건에 직전 턴이 없다. 고른 턴만 남기지 말고 그 앞 턴도 함께 넘길 것
status : NO DATA
```

### ② 1번 턴은 지목할 수 없다

앞 턴이 없으므로 판정할 답변이 없다. 세어서 알려주고 건너뛴다.

### ③ 지목했는데 로그에 없으면 세어서 알려준다

```
  운영 필터가 고른 턴 (turns.json)         1,204
  로그에 없는 턴                           1,198   (-6)
  직전 턴이 없어 판정 불가                 1,191   (-7)
```

**드롭은 전부 이름을 갖는다.** 조용히 줄어들면 목록이 잘못됐는지 로그가 잘못됐는지
알 수 없다.

## 4. 필터가 하지 않아도 되는 것

| | 왜 |
|---|---|
| 2턴 이상 대화인지 확인 | 받는 쪽이 어차피 확인한다. 1턴짜리를 지목하면 세어서 알려준다 |
| 로그를 잘라 넘기기 | 목록이 곧 필터다. 자르면 ①에 걸린다 |
| `Case` 를 만들어 넘기기 | 짝짓기는 이쪽 일이다 (2장) |
| 라벨 점수 재계산 | 무엇을 볼지 정했으면 끝이다 |

---

## 5. 이 저장소 필터의 조건들 (참고용)

같은 판단을 그쪽에서 구현할 때 참고하라고 적어 둔다. **그대로 따를 필요는 없다** —
필터 로직은 그쪽 것을 쓴다.

| 조건 | 무엇을 보나 |
|---|---|
| 진단 가능 후속 턴 | 2턴 이상 대화의 후속 턴 (직전 턴이 실제로 있어야 한다) |
| 직급 · 부서 · 직무 · 직위 | 사용자 메타 |
| 턴 구간 | `2-`, `2-4` 같은 구간 |
| 기간 | `use_date` 가 켜져 있을 때만 |
| eval · emotion 점수 구간 | 확률가중 기대점수로 다시 계산해서 본다 |
| eval · emotion 라벨 | 표기 변형을 흡수해 대조한다 |

**점수를 다시 계산하는 이유** — 기록된 `llm_eval_score` 는 그때의 점수표로 계산된
값이다. 점수표를 바꾸면 낡은 값이 되므로 `llm_alternatives` 에서 다시 계산해야 한다.

```
score = Σ(확률 × 라벨점수) / Σ확률
```

**라벨 표기가 세 군데에서 다르다.** 필터 파일은 붙여쓰고, taxonomy 문서는 띄어쓰고,
로그의 `result` 값은 또 다를 수 있다. 문자열을 그대로 비교하면 **에러 없이 0건**이
나온다 — 이 코드베이스에서 가장 찾기 어려운 실패다. 그쪽에서 구현할 때도 공백·유니코드
정규화를 넣어 두는 편이 낫다.

---

## 6. 받는 쪽의 출력

`--turns` 로 넘겼든 `--filter-data` 로 넘겼든 이후는 같다.

```
output/conv_parsed_20260901-120138.json    분류 결과
output/run_summary_20260901-120138.txt     RUN SUMMARY 사본
```

결과 JSON 은 입력 로그와 같은 `users → conversations → turns` 모양을 유지하고, 판정한
턴에 `classification` 이 붙는다. 원본 로그 옆에 두고 조인할 수 있다.

무엇이 어떤 case 로 갔고 왜 그렇게 됐는지는 [`docs/process_flow.md`](../docs/process_flow.md) 에
있다.
